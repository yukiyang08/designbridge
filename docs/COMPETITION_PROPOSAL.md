# DesignBridge — 從一句話到一張可施工、可採購的室內設計

**商業競賽計畫書**

---

## 一、前言

裝修是多數人一生中金額最大、卻最缺乏決策依據的消費行為之一。一般屋主在與設計師溝通前，心中往往只有一句模糊的「我想要北歐風、動線要順」，接下來卻要面對三道門檻：

**第一道是「說不清楚」。** 屋主無法把想像視覺化，設計師只能靠經驗猜測；來回修改的溝通成本，在設計案的前期往往佔去可觀的時間。

**第二道是「看不到後果」。** 傳統 3D 家配軟體（SketchUp、Planner 5D、酷家樂等）雖然精準，但需要人工拖拉建模、有明顯的學習曲線，不是一般屋主能直接上手的工具。

**第三道是「算不出錢」。** 就算看到了漂亮的效果圖，屋主仍然不知道這個空間要花多少錢、哪些家具買得到、哪裡可以退一步省下預算。效果圖與採購清單之間是斷開的。

近兩年生成式 AI 讓「看到想像」這件事變得極為便宜——但也帶來一個新問題：**AI 畫得出漂亮的房間，卻畫不出「你家那間 8 坪、有一扇窗在北邊、床不能對門」的房間。** 擴散模型不理解坪數、動線寬度與家具尺寸，它只是在生成一張好看的圖片。

DesignBridge 要解決的正是這個落差：**讓生成式 AI 的表現力，長在可計算的空間幾何上，並且一路接到真實的採購清單。**

## 二、創意描述

### 2.1 核心創意：在「座標」與「像素」之間架一座橋

本專案的名稱來自它的核心技術主張——**Bridge**。

精準的空間規劃需要**座標**：家具的位置、尺寸、彼此的間距、與牆與門窗的關係，這些都是可以計算、可以驗證、可以最佳化的數值問題。

但生成式影像模型（FLUX、Stable Diffusion）**讀不懂座標**。把「沙發在 x=0.06, y=0.30」寫進提示詞，模型只會忽略它。這是目前所有「AI 室內設計」工具共同的天花板：要嘛精準但不好看，要嘛好看但不受控。

DesignBridge 的創意是：**不把座標翻譯成文字讓模型猜，而是把座標渲染成模型看得懂的「幾何條件影像」。**

```
使用者需求（自然語言 + 坪數 + 房型 + 生活條件）
      ↓  LLM 語意規劃：要哪些家具、大致擺哪
      ↓  硬約束修正 + 爬山最佳化：把「大致」變成「精確」
2D 平面配置圖（可拖拉編輯，人看得懂）
      ↓  ★ 透視投影：把俯視座標投影成 3D 視角的深度圖
深度圖（ControlNet 看得懂的幾何條件）
      ↓  FLUX depth-ControlNet
寫實效果圖（人看得懂，且真的照著配置畫）
      ↓  視覺辨識 + 向量檢索
家具採購清單與報價
```

這條鏈路讓「精準」與「好看」不再互斥：**幾何由最佳化演算法保證，美感由擴散模型負責。**

### 2.2 第二層創意：讓「設計知識」可以被編輯，而不是被寫死

室內設計的規則（開門不見床、書桌不背門、走道至少留 60 公分、床側要留下床通道、有小孩要避免尖角、有輪椅需求要加寬動線）是**領域知識**，不是程式邏輯。

一般做法是把這些規則寫死在程式碼裡，導致每加一條規則就要改一次核心演算法。

DesignBridge 把這些規則外部化成 **Skill Card**——帶 YAML frontmatter 的 Markdown 檔案，宣告觸發條件、執行順序、可調參數與對應的檢查函式，由 registry 動態載入。

目前已收錄 21 張卡片：

| 類別 | 卡片 |
|---|---|
| 幾何約束（6） | 貼牆吸附、語意間距、書桌與床分離、床側通道、上下舖梯位、床不緊貼窗 |
| 風水禁忌（12） | 開門不見床、開門不見灶、開門不見廁、穿堂煞、床頭不靠窗、書桌不背門、沙發不背窗、灶後不宜空、門不對鏡、鏡不照床、書桌不正對窗、水火不相容 |
| 生活需求（3） | 有小孩、有寵物、輪椅無障礙 |

**加一條新規則＝加一個資料夾**，不必動核心程式。這讓系統具備了被設計師社群共同維護、甚至地域化（華人風水 vs. 歐美無障礙法規）的可能性。

### 2.3 第三層創意：效果圖不是終點，是採購的起點

多數 AI 室內設計工具在「產出漂亮圖片」處停止。DesignBridge 把這張圖再往前推一步：

用視覺模型在成圖上辨識家具並框出位置 → 裁切後轉成 CLIP 向量 → 到 IKEA 台灣商品向量庫做相似度檢索 → 給出可點擊購買的真實商品與價格。

**設計圖與購物車之間，第一次是連通的。**

## 三、系統功能簡介

### 3.1 四條入口流程

系統不強迫使用者走同一條路，而是依據手上「已有什麼」提供四個入口：

| 入口 | 適用情境 | 流程 |
|---|---|---|
| **從零生成** | 只有想法，連格局都還沒定 | 空間設定 → 3D渲染圖 → 微調編輯 → 預算估計 |
| **繪製平面圖** | 知道坪數與房型，想先看配置 | 空間設定 → **繪製平面圖** → 3D渲染圖 → 微調編輯 → 預算估計 |
| **上傳平面圖** | 手上有建商平面圖 | 上傳平面圖 → **選擇房間** → 繪製平面圖 → 3D渲染圖 → 微調編輯 → 預算估計 |
| **上傳空間照** | 已入住，想看改造後的樣子 | 空間照片上傳 → 3D渲染圖 → 微調編輯 → 預算估計 |

上傳整戶平面圖時，系統會先用視覺模型自動分割出各個房間，使用者點選要設計的那一間即可；只偵測到一間時自動跳過該步驟。

### 3.2 核心功能模組

**① 需求解析（Requirement Analyzer）**

把自然語言需求解析成結構化 JSON：房型、坪數、風格傾向、必須保留／新增／移除的家具、家庭成員狀況、不可動用區域。LLM 解析失敗時自動退回規則式解析，確保流程不中斷。

**② 佈局規劃（Layout Agent）**

- LLM 負責語意決策（要哪些家具、大致在哪），**不負責精算幾何**
- 硬約束層依固定順序執行：家具增刪 → 指令式搬移 → 避開禁區 → 邊界夾取 → 碰撞分離 → 約束卡片
- 幾何最佳化採**隨機爬山法（2000 步、高斯退火提議）**，對五項軟性指標搜尋：動線（35%）、重心平衡（25%）、視覺焦點（20%）、自然採光（10%）、人體工學（10%）
- 內建 27 種家具的預設尺寸，LLM 未給或給出離譜值時自動兜底
- **單調性保證**：最佳化後的結果會與最佳化前的基準在相同條件下比分，取較佳者，演算法永遠不會交回比輸入更差的佈局

**③ 平面圖製圖**

以 pycairo 向量繪製符合建築製圖慣例的平面圖：牆體實心、每公尺格線、開門弧線、三線窗符號、尺寸標註與比例尺。家具不是一律畫方框，而是依類別畫語意符號（椅為圓形、地毯為虛線雙框、床有床頭板與枕頭、衣櫃有把手圓點），並標註真實公尺尺寸。

**④ 互動編輯**

前端以 SVG 重繪同一份配置，家具可拖曳、縮放、旋轉；另提供 Three.js 3D 預覽可即時檢視。編輯結果回傳後端，用**同一支製圖函式**重繪，確保前端預覽與後端出圖完全一致。

**⑤ 渲染（Renderer）**

將配置座標投影成透視深度圖，作為 FLUX depth-ControlNet 的空間條件。深度圖中每件家具以**語意輪廓**呈現（桌子為懸空桌面加四腳、沙發為座墊加椅背加扶手、立燈為細桿加燈罩），而非一律擠成實心長方體——後者會讓模型只畫得出方塊。同時搭配家具 footprint 的 Canny 邊緣圖作為第二路控制，鎖定遠景家具的位置。

**⑥ 風格檢索**

內建 9 種風格（現代、鄉村、古典、北歐、工業、日式、美式、奢華、其他）。以 Supabase pgvector 做語義檢索取得風格參考圖與提示詞，本地 ChromaDB 作為備援。使用者亦可自行上傳風格參考圖，由視覺模型即時分析。

**⑦ 局部微調（Refine）**

使用者可在成圖上塗抹遮罩，指定「只改這一塊」，系統以 inpainting 模型局部重繪，不影響畫面其餘部分。

**⑧ 360° 環景與 3D 點雲**

由成圖反推深度後重建室內幾何，產出可用滑鼠環視的等距柱狀投影全景圖，以及可旋轉檢視的 3D 點雲與 GLB 模型。

**⑨ 估價（Quotation）**

視覺模型辨識成圖中最多 8 件主要家具並回傳 bbox → 裁切 → CLIP 向量 → IKEA 台灣商品庫（380 項）向量檢索 → 每件給出 top-3 候選商品、價格與購買連結。相似度低於門檻（0.75）時不硬塞結果，改由 LLM 估算市場行情價，避免給出錯誤推薦。

**⑩ 品質評估**

以 CLIP 計算成圖與需求描述的語義相似度，作為迭代是否收斂的依據。

### 3.3 工作流編排

整條流程以 LangGraph StateGraph 編排，具備條件路由與多輪迭代能力：

```
START → 需求解析 → 視覺預處理 → 設計總監（路由）
                                    ├→ 調整代理（既有設計微調）
                                    └→ 佈局＋風格代理（全新設計）
                                            ↓
                                         渲染 → 3D 重建 → 品質評估 → END
```

估價代理刻意**不放進自動流程**——它耗時約 30–40 秒且不影響成圖本身，改由使用者按下按鈕才觸發獨立端點，避免每次生成都拖慢整體體驗。

## 四、系統特色（競品分析）

### 4.1 競品格局

目前市場上與「AI 室內設計」相關的產品，可歸納為四類：

| 類別 | 代表產品 | 運作方式 | 侷限 |
|---|---|---|---|
| **通用生成式 AI** | Midjourney、DALL·E、Stable Diffusion | 純文字生圖 | 畫面好看但完全不受控；無法指定坪數、動線、家具尺寸；與現實空間無關 |
| **AI 室內換裝** | Interior AI、REimagine Home、RoomGPT、Collov 等 | 上傳照片 → img2img／inpaint 換風格 | 沿用原照片的空間結構，**只換材質風格、不重新規劃配置**；無法回答「這間空房該怎麼擺」 |
| **傳統 3D 家配軟體** | SketchUp、Planner 5D、Homestyler、酷家樂 | 人工拖拉建模 | 精準但需要學習；配置全靠使用者自己想，軟體不提供規劃建議；非生成式，寫實度依賴算圖時間 |
| **品牌電商導購** | IKEA Kreativ 等 | 空間掃描 + 自家型錄擺放 | 綁定單一品牌；以商品展示為目的，非設計規劃工具 |

> 註：上表為各類別的通則性描述，個別產品的功能持續演進。

### 4.2 DesignBridge 的差異化定位

**特色一：同時具備「演算法規劃」與「生成式渲染」的閉環**

通用生成式 AI 好看不受控；換裝類工具受控但不規劃；傳統軟體規劃但要人工。DesignBridge 把三者接起來——**演算法決定家具擺哪（可驗證），擴散模型決定它長什麼樣（好看）**。這是本系統最根本的差異，也是其他三類產品在架構上都沒有走的路。

**特色二：空間條件是「幾何」而非「文字」**

同業若要控制生成結果，普遍做法是把需求寫進提示詞。本專案實測顯示擴散模型對空間文字的遵循度極低——把佈局描述加進提示詞，反而會稀釋風格訊號，讓成圖比不加還不準。本系統改以投影深度圖 + footprint 邊緣圖雙路 ControlNet 作為條件，是**可量測、可回歸測試**的控制手段：專案內附的自動化測試會斷言「桌子的深度輪廓必須比同尺寸櫃子少佔 20% 以上像素」這類幾何性質。

**特色三：語意化家具輪廓**

一般 3D-to-depth 做法是把每件家具擠成實心長方體。深度 ControlNet 只看得到輪廓，餵它方塊就只會畫出方塊——這是「AI 室內圖看起來很假」的技術根源之一。本系統將家具依類別拆解成子塊（桌面懸空見腳、沙發有椅背扶手、電視是薄板），讓深度圖的輪廓本身就攜帶家具身分資訊。

**特色四：在地化的設計規則庫**

國外產品不會處理風水。本系統以 Skill Card 形式收錄開門不見床、書桌不背門、開門不見灶、開門不見廁所、穿堂煞等 12 條華人市場高度在意的禁忌，使用者在介面勾選後，規則會自動寫進佈局的硬約束層並在收斂後逐條驗證，並與有小孩、有寵物、輪椅無障礙等生活需求並列為可插拔規則。這是針對台灣／華語市場的直接差異化。

**特色五：從設計圖直接接到採購**

同業的產出終點是圖片。本系統的產出終點是**一份可點擊購買的清單與總價**。對屋主而言，這是「好看」與「買得起」之間的關鍵一哩路。

**特色六：四條入口，涵蓋不同準備程度的使用者**

不論使用者手上是一句話、一張建商平面圖、還是一張自家客廳的照片，都有對應的進入點。同業多半只支援單一入口（通常是上傳照片）。

**特色七：多重備援設計，可用性優先**

雲端 LLM 失效退回規則式解析；Supabase 不可用退回本地向量庫，再退回關鍵字搜尋；向量製圖庫缺失退回點陣繪圖；3D 匯出失敗不影響全景產出。系統在任一外部服務中斷時仍能降級運作，而非整條流程失敗。

### 5.2 值得說明的技術決策

**為什麼佈局最佳化用爬山法而不是讓 LLM 迭代？**

舊版設計是每輪把五個純量分數丟回給 LLM 重猜，一輪一次 API 往返卻沒有任何可據以行動的資訊。改成數值最佳化後，**同樣時間可以評估數千個候選，而且結果完全可重現**（固定亂數種子）。LLM 保留在它真正擅長的語意層——決定「這間房該有什麼家具」。

**為什麼不做完整 3D 建模？**

使用 Blender 或 3D 生成模型（TripoSR 等）的風險高、家具品質不穩、運算成本大。本系統改以純 NumPy 的長方體投影產生深度條件——**輕量、可測試、毫秒級**，把寫實度的責任交給擴散模型，各司其職。

**為什麼佈局文字不注入生成提示詞？**

如特色二所述，實測顯示加入佈局描述反而稀釋風格訊號。因此佈局資訊**只走 ControlNet 幾何通道**，文字提示詞專注於風格與材質。

## 六、系統使用對象

### 6.1 主要對象

**① 準備裝修的一般屋主與租屋族**

- 痛點：不知道自己想要什麼、說不清楚、無法預估預算
- 本系統價值：幾分鐘內從一句話得到平面配置、寫實效果圖與採購清單，在花錢之前先確認方向；可反覆試驗不同風格與配置而零成本

**② 室內設計師與接案工作者**

- 痛點：前期提案耗時，客戶反覆修改；每一版方案都要重畫
- 本系統價值：作為**提案加速器**——快速產出多個方案供客戶挑選，收斂方向後再投入精細設計；平面圖符合建築製圖慣例，可直接作為溝通底稿

**③ 房仲與建商**

- 痛點：空屋與預售屋難以讓買方想像實際居住樣貌；實體樣品屋成本高昂
- 本系統價值：上傳建商平面圖即可產出多種風格的樣品屋視覺，360° 環景可嵌入銷售網頁

### 6.2 延伸對象

**④ 家具與家飾電商**

系統的估價模組可對接任何商品型錄，成為「看圖買整套」的導購入口；目前以 IKEA 台灣型錄作為概念驗證。

**⑤ 有特殊居住需求的家庭**

有幼兒、寵物、或輪椅使用者的家庭，可透過對應的規則卡片讓系統在規劃階段就納入安全與無障礙考量——這是通用工具不會處理的需求。

## 七、系統使用環境

### 7.1 使用者端

| 項目 | 需求 |
|---|---|
| 裝置 | 桌機、筆電、平板（響應式介面） |
| 瀏覽器 | Chrome / Edge / Safari 等現代瀏覽器，需支援 **WebGL**（3D 預覽與環景檢視） |
| 網路 | 需連網（影像生成為雲端推論） |
| 安裝 | **無需安裝任何軟體**，開啟網頁即可使用 |

### 7.2 伺服器端

| 項目 | 需求 |
|---|---|
| 作業系統 | Windows / macOS / Linux（開發環境為 Windows 11） |
| 執行環境 | Python 3.11+（開發環境 3.13）、Node.js 20.19+ |
| 硬體 | **不強制 GPU**——影像生成走雲端推論；本地僅執行深度估計與 CLIP 等輕量模型，CPU 即可運作。若配置 GPU 可改走本地推論以降低 API 成本 |
| 儲存 | 生成產物（效果圖、深度圖、平面圖、GLB）寫入本地 `artifacts/` 目錄，並以靜態路徑對外提供 |

### 7.3 外部服務依賴

| 服務 | 用途 | 缺席時的降級行為 |
|---|---|---|
| Google Gemini API | 需求解析、佈局規劃、家具辨識 | 退回規則式解析與預設樣板佈局 |
| fal.ai | FLUX 生成與 ControlNet 推論 | 退回 Hugging Face 推論或本地模型 |
| Hugging Face API | 模型推論備援 | — |
| Supabase（pgvector + Storage） | 風格庫、商品庫向量檢索 | 退回本地 ChromaDB，再退回關鍵字搜尋 |

系統以環境變數集中管理所有設定（模型名稱、控制強度、最佳化步數等），可在不改動程式碼的情況下調整行為或切換供應商。

## 八、結語

DesignBridge 的出發點不是「再做一個 AI 生圖工具」，而是回答一個具體的技術問題：**如何讓生成式 AI 的輸出，服從於真實世界的幾何約束？**

我們的答案是把設計流程拆成兩層，各自交給擅長的技術：

**可計算的部分交給演算法**——家具擺哪、走道多寬、床能不能對門，這些有明確對錯，用最佳化與規則引擎處理，結果可驗證、可重現、可回歸測試。

**不可計算的部分交給生成模型**——材質、光影、氛圍、質感，這些沒有標準答案，擴散模型做得比任何程序化渲染都好。

兩層之間的橋樑，就是把座標投影成深度圖的那一步。這座橋讓系統同時擁有「聽得懂 8 坪套房、床不能對門」的精準，與「一張可以直接拿去提案」的美感。

再往前一步，我們把這張圖接到了真實的商品與價格——因為對屋主而言，一張再好看的效果圖，如果不知道要花多少錢、東西哪裡買，就仍然只是一張圖。

從一句話到一份可施工、可採購的方案，DesignBridge 想縮短的，是想像與現實之間那段最昂貴的距離。
