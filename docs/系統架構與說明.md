# 系統架構與說明

> 本文內容依 `main` 分支（commit f3a4a3e3）之實作撰寫。

## 一、系統整體架構

DesignBridge 採前後端分離架構：前端以 Vue.js 3 建構線性精靈（Wizard）式操作介面；後端以 FastAPI 提供 RESTful API，並以 LangGraph 作為多代理人（Multi-Agent）流程管理框架；資料層採 Supabase（PostgreSQL + pgvector），負責風格參考圖與家具商品之向量檢索。影像生成主要透過 fal.ai 雲端推論服務執行 FLUX.1 系列模型，語意理解與視覺辨識則由 Google Gemini 負責。

系統核心決策由四個 AI 代理人分工處理：需求分析代理人（Requirement Analyzer Agent）、佈局規劃代理人（Layout Agent）、設計微調代理人（Design Adjuster Agent）及預算規劃代理人（Budget Agent），並搭配視覺前處理模組（Vision Preprocessor）、風格模組（Style Module）、提示詞統整模組（Prompt Composer）、影像生成模組（Renderer）及生成品質評估模組（CLIP Evaluator）等功能性組件。各節點透過 LangGraph 管理之全域共享狀態（`DesignBridgeState`）傳遞需求結構、視覺特徵、場景圖與生成結果。

考量回應時間與使用體驗，預算規劃（約 30–40 秒）與 360° 全景圖生成不影響主效果圖，故不納入自動流程，而設計為使用者於結果頁按需觸發之獨立 API（`/api/quotation`、`/api/generate-panorama`）。

### 1.1 設計起點

系統提供三種設計起點，最終皆匯入同一條 LangGraph 生成流程。三種起點皆可於進階設定中補充坪數、畫面比例、家庭結構與風水需求。

1. **從平面圖開始**：
   - *自動生成整層平面圖*：使用者輸入各空間數量（臥室、浴室、客廳、廚房、陽台等）與房屋總坪數，由平面圖生成模組以幾何演算法切分房間，自動產生含牆體隔間、門窗與尺寸標註之整層 CAD 平面圖（`/api/generate-room-plan`）。
   - *上傳既有 CAD 平面圖*：由 Gemini Vision 辨識圖中各房間之邊界（`/api/detect-rooms`），並解析房間尺寸、門窗與既有家具位置（`/api/parse-floor-plan`）。
   - 使用者選擇其中任一房間後，進入家具配置。
2. **上傳現況照片**：使用者上傳一張空間現況照片並以文字描述改造方向，系統經 Vision Preprocessor 分析格局（深度與語義分割）後直接生成渲染圖，於保留原有空間結構的前提下重新設計，適合既有空間之翻新規劃。
3. **從零開始描述**：使用者選擇空間類型（客廳、臥室、廚房、浴室或自訂）並以文字描述理想樣貌，系統直接生成渲染圖。

### 1.2 設計流程

1. **生成 CAD 平面配置圖（僅平面圖起點）**：Layout Agent 依房間尺寸、門窗與動線自動排出預設家具配置，使用者可於 2D 平面上自由增減、拖曳、縮放家具；確認後之配置即作為後續渲染之場景圖，不再重新規劃（`/api/generate-layout`、`/api/render-floor-plan`）。
2. **3D 渲染圖生成**：使用者輸入風格描述與需求後，Style Module 推薦風格參考圖，使用者挑選後依該風格生成渲染圖（`/api/generate`，即 1.3 節之 LangGraph 流程）。支援兩種方式：
   - *整層一次生成*：完成一間房後，可將相同風格設定「套用到其他房間」，系統批次生成其餘房間，並共用同一組風格參數，維持整層風格一致；
   - *單一房間分次生成*：逐一挑選房間，分別輸入不同風格與需求後各自生成。
3. **360° 環景圖**：將渲染圖以 FLUX Fill 外擴繪製並拼接為環景圖，使用者可拖曳視角、縮放檢視（`/api/generate-panorama`）。
4. **微調編輯**：使用者以畫筆圈選不滿意之區塊並輸入修改需求，由 Design Adjuster 僅重繪該區域，其餘部分保持不變（同樣經 `/api/generate`，由 Requirement Analyzer 判定為局部修改分支）。
5. **預算估計**：Budget Agent 辨識效果圖中之家具，媒合真實品牌商品與價格並加總；使用者可切換候選商品、開啟購買連結，並收藏設計方案（`/api/quotation`、`/api/history/{task_id}/favorite`）。

### 1.3 LangGraph 生成流程

```
START → Requirement Analyzer → Vision Preprocessor ─┬─(新設計)→ Layout & Style → Prompt Composer ─┐
                                                     └─(局部修改)→ Design Adjuster ─────────────────┤
                                        END ← CLIP Evaluator ← Renderer ←──────────────────────────┘
```

- **分流機制**：由 Requirement Analyzer 依使用者語意判斷為「新設計」或「局部修改」，於視覺前處理後進入不同分支。
- **新設計分支**：Layout Agent 與 Style Module 於同一節點執行，產出場景圖與風格參數，再由 Prompt Composer 整合為最終提示詞後交由 Renderer 生成。
- **局部修改分支**：Design Adjuster 直接對既有效果圖進行遮罩重繪（Inpainting），不經過 Prompt Composer，以避免改動未指定區域。
- 所有分支最後皆經 CLIP Evaluator 評估生成結果與需求之一致性。

## 二、各模組說明

### 2.0 平面圖生成模組 Room Plan Generator

供「從平面圖開始」起點使用，不經過 LangGraph。依使用者輸入之房間數量與總坪數，換算總面積後以幾何切分演算法分配各房間位置與大小，再推導牆體、門窗開口，輸出含尺寸標註之 SVG 平面圖。此模組為規則式運算，結果穩定可重現，產出之房間邊界與門窗位置即作為 Layout Agent 之輸入。

### 2.1 需求分析代理人 Requirement Analyzer Agent

以 Gemini 大型語言模型將使用者之自然語言需求（可附照片）解析為結構化需求 JSON，內容包含空間類型、空間尺寸、門窗位置、風格偏好、家具需求、預算、英文設計描述，以及是否需要重新規劃佈局（`hint_layout`）等欄位。

此代理人同時負責流程路由：判斷使用者意圖為整體設計或局部修改，決定後續進入 Layout & Style 分支或 Design Adjuster 分支。若使用者勾選風水規則，亦於此階段併入結構化需求，作為後續佈局之約束條件。Gemini 呼叫失敗時，退回以規則式解析，確保流程不中斷。

### 2.2 視覺前處理模組 Vision Preprocessor

針對使用者上傳之現況照片，於本地端執行兩項模型推論：

- **深度估計**：採用 Depth Anything V2 推導畫面中物件之相對距離與空間幾何關係，輸出深度圖作為 Renderer 中 ControlNet-Depth 之控制訊號。
- **語義分割**：採用 UPerNet（ConvNeXt backbone，ADE20K 類別）辨識牆面、地板、天花板、門窗與主要家具，產生可索引之語義遮罩，供 Renderer 產生邊緣控制訊號，以及 Design Adjuster 定位修改目標。

系統依使用者輸入路徑分流處理深度圖來源：若使用者提供現況照片，深度圖由 Depth Anything V2 直接推導，並由深度圖反推房間地平面與既有家具位置；若使用者從空白畫布開始，則由 Layout Agent 產出之場景圖（家具三維座標與尺寸），經虛擬相機投影運算轉換為深度圖。此機制確保生成結果始終具備明確之幾何依據，避免傳統 AI 生圖僅依賴語言描述所導致的空間邏輯錯誤（如家具懸空、穿牆、比例失真）。

### 2.3 佈局規劃代理人 Layout Agent

Layout Agent 以空間可行性與動線合理性為優化目標，採「大型語言模型提案 + 約束式修正 + 幾何最佳化」之混合求解方式：

1. **LLM 提案**：由 Gemini 依房間邊界、門窗、固定結構與家具需求，提出初始家具擺放方案。
2. **硬約束修正**：套用不可違反之空間規則（如家具不得重疊、不得超出牆面、不得阻擋門窗、需保留通道寬度），並可疊加使用者選擇之風水規則。各約束以 `SKILL.md` 規則檔集中定義，每條規則皆有對應之修正（enforce）與驗證（verify）函式，便於擴充。
3. **幾何最佳化與軟約束評分**：以幾何最佳化器微調家具位置，並依動線、對齊、功能分區等軟約束計算評分，迭代至評分達門檻（0.65）或達最大迭代次數為止。
4. **輸出**：產出包含家具位置（pose）、尺寸（size）與家具間關係之場景圖（Scene Graph），並投影為 ControlNet 深度圖；同時轉為佈局文字描述，作為 Prompt Composer 之佈局輸入。

若 LLM 提案失敗，系統退回預設佈局範本。佈局規劃僅在使用者要求重新配置空間時執行；若使用者已於 2D 平面手動調整家具，則直接沿用該場景圖重新投影，不重複規劃。

### 2.4 風格模組 Style Module

Style Module 依使用者輸入之文字需求，向風格資料庫進行語意檢索，回傳語意相近之候選參考圖供使用者挑選；亦支援以選定之圖片為錨點「找相似風格」。檢索方式為將查詢文字以 BGE-M3 模型轉為向量，與資料庫中每張參考圖之風格描述向量進行 pgvector 相似度比對。

使用者選定參考圖後，系統讀取該圖對應之 Style Profile（材質、色彩配置、氛圍描述、建議提示詞與風格強度），以及該圖所屬風格分類。風格分類用於載入 Renderer 對應之風格 LoRA 權重，Style Profile 則送入 Prompt Composer，與 Layout Agent 之佈局資訊共同構成最終生成提示詞。

系統共定義 8 種風格分類：現代簡約、奶油溫馨、無印生活、北歐自然、現代工業、日式禪意、美式暖居、現代輕奢，每種風格皆獨立訓練一組 LoRA。相較於僅依賴文字提示詞控制風格，微調後的模型能穩定產出符合該風格視覺語彙的結果，降低生成過程中的風格漂移與不確定性。完整訓練流程詳見圖二。

### 2.5 提示詞統整模組 Prompt Composer

生成提示詞來自三個彼此獨立之來源：使用者需求之設計描述、風格參考圖之 Style Profile，以及 Layout Agent 之家具配置。若直接串接，常出現風格互相矛盾（如使用者要求輕奢、參考圖卻為工業風）或家具描述衝突（如風格描述為圓桌、佈局卻為方桌）。

Prompt Composer 以 Gemini 將三者整合為單一、無衝突之英文提示詞，整合原則為：使用者描述決定整體美學方向；佈局之家具資訊視為不可更動之事實；風格參考僅補充不衝突之材質、光線與氛圍詞彙。若無需整合之內容（如純換風格且無家具資訊），則略過此步驟以節省約 12–18 秒之 LLM 呼叫。

### 2.6 影像生成模組 Renderer

Renderer 採用 FLUX.1-dev 作為基底模型（經 fal.ai 之 FLUX-general 端點推論），依 Style Module 之風格分類動態載入對應風格 LoRA 權重，並同時疊加兩組 ControlNet：

- **ControlNet-Depth**：以深度圖約束空間結構與家具位置；
- **ControlNet-Canny**：以語義分割產生之邊界圖補強牆角、門窗等硬邊界。

兩組控制訊號僅作用於去噪過程前段，使結構先行固定、後段由模型自由生成材質細節，以兼顧幾何正確性與畫面品質。換風格時沿用前次生成之隨機種子（seed），讓構圖維持一致、僅改變風格。若主要生成端點失敗，系統依序退回其他生成後端，確保使用者仍能取得結果。

**360° 全景圖**：使用者於結果頁按需觸發後，系統以生成之效果圖為中心，透過 FLUX Fill 外擴繪製（Outpainting）向左右延伸畫面，拼接為 2:1 等距長方投影（Equirectangular）全景圖，供使用者以沉浸式視角瀏覽空間。

### 2.7 設計微調代理人 Design Adjuster Agent（局部修改）

Design Adjuster 依使用者之修改指令（如「把沙發換成L型」「移除植栽」）擬定局部修改計畫，並於鎖定未改動區域之結構與光影的前提下，只重繪指定區域：

1. **遮罩產生**：使用者可於畫面上手繪框選目標；若未框選，則依語義分割結果定位目標物件，找不到時改由 Gemini Vision 回傳目標之邊界框。之後以 SAM 2 進行像素級精修，取得物件完整輪廓。若為替換成不同種類之物件，遮罩外擴為矩形，以容納新物件之形狀。
2. **提示詞改寫**：由 Gemini 檢視遮罩區域，將修改指令改寫為修改後該區域之描述。
3. **重繪**：純移除任務採 LaMa 進行背景重建；替換或修改任務採 FLUX.1 Fill 進行遮罩區域重繪。

### 2.8 預算規劃代理人 Budget Agent

使用者於結果頁按下「取得家具報價」後觸發，流程如下：

1. 以 Gemini Vision 辨識效果圖中之家具品項與位置（邊界框）；
2. 依邊界框裁切家具影像，以 CLIP 轉為影像向量；
3. 於家具資料庫進行 pgvector 相似度檢索，每項家具回傳前 3 名真實商品候選（含品名、價格、規格、連結）；
4. 使用者可切換候選商品，系統即時彙整家具清單與總花費。

若資料庫無相符商品，則由 LLM 依品項估算參考價格。

### 2.9 生成品質評估模組 CLIP Evaluator

於每次生成後，以 CLIP 計算效果圖與使用者需求描述之語意相似度，作為生成結果是否符合需求之量化指標，並記錄於生成結果中，供後續分析與實驗比較使用。

## 三、資料庫與資料來源

| 資料庫 | 儲存位置 | 內容 | 使用模組 |
|---|---|---|---|
| 風格資料庫 | Supabase `style_images` 表（pgvector） | 約 3,000 張室內設計參考圖、風格分類標記、空間類型標記、Style Profile，以及由 Style Profile 文字轉成之 BGE-M3 向量 | Style Module |
| 家具資料庫 | Supabase pgvector（本地 `ikea_embeddings.npz` 為備援） | 台灣 IKEA 家具商品之品名、類別、價格、規格、商品圖之 CLIP 向量 | Budget Agent |
| 使用者歷史紀錄 | 後端 `artifacts/history.json` | 歷次生成之需求、效果圖、風格、耗時明細與收藏標記 | 歷史紀錄頁 |

風格資料庫之 Style Profile 於離線前處理階段預先建立：自台灣室內設計平台蒐集案例圖片，由視覺語言模型標註風格描述、材質、色彩與建議提示詞，再以 CLIP 零樣本分類標記空間類型，最後計算向量上傳 Supabase，使線上檢索時無需即時分析圖片。

## 四、技術選型總表

| 層級 | 技術 |
|---|---|
| 前端 | Vue.js 3、Vite |
| 後端 | FastAPI、LangGraph |
| 資料庫 | Supabase（PostgreSQL + pgvector） |
| 語言與視覺理解 | Google Gemini |
| 深度估計 / 語義分割 | Depth Anything V2、UPerNet |
| 影像生成 | FLUX.1-dev + 風格 LoRA + ControlNet（Depth、Canny），經 fal.ai 推論 |
| 局部重繪 | SAM 2、LaMa、FLUX.1 Fill |
| 全景圖 | FLUX Fill Outpainting |
| 向量模型 | BGE-M3（風格文字）、CLIP（家具影像、品質評估） |
