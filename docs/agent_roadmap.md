# 代理人架構：現況與改善規劃

> 本文件的「改善」與「未來展望」皆為規劃，**尚未實作**，不可在對外文件寫成已完成。
> 文件數據（A.2.1、A.2.2、A.2.6）須在實作並重測後才能更新。

## 1. 設計原則

主觀偏好由使用者決定，客觀可驗證的部分交給代理人，代理人只能在使用者劃定的範圍內動作。

| 決策類型 | 例子 | 誰決定 |
|---|---|---|
| 主觀偏好 | 風格、參考圖、要不要某件家具、接不接受結果 | 使用者 |
| 客觀約束 | 碰撞、動線、貼牆、門不被擋 | 代理人（程式驗證） |
| 規則型建議 | 風水、人體工學 | 代理人提議，使用者可關閉 |
| 文字整合 | 合成生圖 prompt | 代理人，使用者描述優先 |

## 2. 代理人的判準

採用 Willison (2025) 的定義：「An LLM agent runs tools in a loop to achieve a goal.」（https://simonwillison.net/2025/Sep/18/agents/）。拆成四項，缺一不可：

- LLM：由 LLM 做判斷或生成。
- 工具：呼叫程式、模型或外部服務（檢索、驗證器、優化器、分割模型等）。
- 迴圈：看結果再調整，不是呼叫一次拿結果。
- 目標：迴圈有明確的完成條件。

另依 Anthropic (2024) 的區分（https://www.anthropic.com/engineering/building-effective-agents）：流程由程式寫死的叫 workflow，由 LLM 動態決定流程的才叫 agent，該定義門檻較高。本系統的流程（條件邊、重試次數）由程式決定，整體屬 workflow；其中符合上述四項的節點，稱為 agent 節點。

對外說法：「含 agent 節點的多步驟 AI 工作流加人機協作」。不自稱 multi-agent：節點之間沒有 LLM 動態分派或互相協商，也沒有找到可引用的低門檻 multi-agent 定義。

逐項對照：

| 模組 | LLM | 工具 | 迴圈 | 判斷 |
|---|---|---|---|---|
| 需求分析 | 有 | 少 | 無 | 否（擴充為對話後再評估） |
| 影像前處理 | 無 | 有 | 無 | 否 |
| 佈局（預設） | 有 | 有（優化器、驗證器） | 無 | 否（workflow） |
| 佈局（開 `LAYOUT_REVIEW_AGENT`） | 有 | 有 | 有（檢查後重排一次） | 是 |
| 風格 | 無 | 檢索 | 無 | 否（使用者選擇，刻意不做成代理人） |
| 提示詞統整（現況） | 有 | 無 | 無 | 否 |
| 提示詞統整（加驗證後） | 有 | 驗證器 | 有 | 是 |
| 局部修改 | 有 | 有（SAM2、LaMa、FLUX Fill、bbox） | 部分（遮罩過小時改用 bbox，不驗證結果） | 邊緣 |
| 渲染 | 無 | 有 | 無 | 否（執行端） |
| 評估（現況） | 無（CLIP） | 無 | 無 | 否 |
| 評估（加需求檢查與一鍵修正後） | 有 | 有（局部修改、提示詞統整） | 有 | 是 |
| 對話式顧問（未來） | 有 | 有（各模組 API） | 有 | 是 |

依目前程式碼的旗標預設值，`LAYOUT_REVIEW_AGENT` 為 true，佈局檢查迴圈會執行，是目前唯一符合的節點；效益與耗時尚未量測，量測後才能對外宣稱有改善。

## 3. 現況與改善

「是否為 agent」依第 2 節的判準：有 LLM、有工具、有看結果再調整的迴圈、有目標才算；「改善後」欄假設該項改善完成。

| 模組 | 現況 | 是否為 agent（現況 → 改善後） | 改善 |
|---|---|---|---|
| 需求分析 | LLM 解析需求，決定路由（新設計或局部編輯）、是否重排空間 | 邊緣：有決策，但單次、無回饋迴圈 → 擴充為對話後才算 | 生成前澄清對話已有；之後擴充成貫穿流程、能記住偏好的對話（見第 5 節） |
| 影像前處理 | 照片深度估計與語意分割，供後續錨定 | 否：純感知工具 → 不變 | 無 |
| 佈局 | LLM 提案一次 → 硬規則修正 → 演算法優化。另有 `LAYOUT_REVIEW_AGENT` 迴圈（預設 true，2026-10-30 起）：規則檢查風水／動線，有問題才交回 LLM 重排一次，更差則保留原佈局。舊的 `LAYOUT_LLM_REFINE`（只回傳分數）已移除 | 是（`LAYOUT_REVIEW_AGENT` 開啟時；關閉則為 workflow） | 見 3.1 |
| 風格 | bge-m3 向量檢索（Supabase pgvector），混合成風格參數 | 否：檢索模組 → 維持否 | 維持模組，不做成代理人（見 3.4） |
| 提示詞統整 | 一次 Gemini 呼叫合併使用者描述、家具事實、風格詞，不檢查輸出 | 否（有 LLM 的函式）→ 加驗證重寫迴圈後是 | 見 3.2 |
| 局部修改 | Vision 判斷意圖，選遮罩來源與修補後端，多層退路 | 接近：有感知、決策、選工具，遮罩過小時會依觀察改用 bbox，但不驗證結果 → 不調整，維持 | 不調整；之後可作為評估節點的修正工具 |
| 渲染 | FLUX 加 ControlNet 生圖，多種後端與旗標 | 否：執行端 → 不變 | 無 |
| 評估 | CLIP 評分，只打分，不影響後續流程 | 否（只評分、不行動）→ 加需求檢查與一鍵修正後是 | 見 3.3 |
| 佈局與風格的節點結構 | 同一節點串行執行，函式名仍叫 `layout_and_style_agent_stub` | 不適用：結構問題 | 見 3.5 |

### 3.1 佈局

問題：優化器只最大化五項分數，沒有擺放常理，動線分數升高，家具位置卻不合理。

1. 先把常理寫成程式可算的規則加進評分（沙發朝向電視、床頭靠牆、餐椅在桌邊、書桌不背對門）。不增加 LLM 呼叫與延遲。
2. 規則分兩組：一組用於優化，一組留作評估，避免自己出題自己考。
3. 規則不夠時才加 LLM 評審迴圈：
   - 最多 2 輪，一次呼叫同時評審並回傳位置修正（delta）。
   - 輸入：房間尺寸與門窗、每件家具座標與朝向、程式算好的事實（五項分數、未滿足的特殊約束、碰撞與間距結果）。
   - 套用 delta 後必經 `_settle`，硬約束由程式把關；優先序為硬約束違規數、軟性分數，變差就退回。
   - 動到 pinned 或使用者指定家具的 delta 一律丟棄。
   - 開關 `LAYOUT_CRITIC`，預設關；LLM 失敗或 JSON 錯誤都退回原版。
4. 失敗原因寫進 state 並顯示在前端，不再只印警告。
5. 介面保留「原始版／優化版」可切換。

驗證：常理規則通過率、硬約束違規數、五項分數、耗時。比較三組：現況（優化器）、評審迴圈、評審迴圈加優化器微調。

### 3.2 提示詞統整

- 輸出 `decisions`（例如「使用者要輕奢，捨棄風格參考中的工業詞」）。
- 程式驗證家具涵蓋、是否被 `max_tokens` 截斷、使用者排除項；不合格帶缺漏項目重寫一次。
- 驗證用程式做，不讓 LLM 自評。優先順序維持：使用者描述、佈局家具事實、風格詞。
- 單次呼叫加決策記錄不算代理人，必須有「驗證失敗後重寫」的迴圈。
- 驗證：驗證失敗率、重寫前後家具涵蓋率、額外耗時。
- 更名：加迴圈前叫「提示詞統整模組」，加了之後叫「提示詞統整代理人」；英文 `Prompt Reconciler`。程式裡 `composer` 不用改。

### 3.3 評估

- 改成視覺 LLM 檢查「需求清單與生成圖」，列出符合與不符合項。
- 不符合項附「一鍵修正」：局部問題呼叫局部修改，整體問題交給提示詞統整重寫並重生。
- 先做成提議，使用者點了才執行；視覺 LLM 的準確率經人工抽樣驗證後，再考慮自動重試一次。
- 迴圈裡用的 LLM 判斷不能同時當文件的成效指標；文件數據另用規則、CLIP 或人工抽樣。
- 修改前保留原圖，使用者可還原。

### 3.4 風格不做成代理人

- 向量檢索加 LLM 重排只是 reranker，不是代理人。
- 風格是主觀偏好，自動代選會犧牲使用者選擇權。
- 只有以下條件成立時才考慮代理人化：複合或模糊需求需要拆解組合、有檢索以外的工具、有客觀回饋驅動迴圈、使用者授權代為決定。
- 若要增加風格參與，只做「風格到佈局」的靜態傾向表（密度、對稱、低矮），影響低權重軟性評分，硬約束不動。

### 3.5 節點結構

- 風格檢索不依賴佈局，拆成兩個並行節點，延遲約等於較慢的一邊。
- 動工前先確認 `core/state.py` 的 `intermediate_outputs` 有 reducer，否則並行寫入會衝突。
- 保留「已有 scene_graph 時只重新投影」的捷徑。

## 4. 建議順序

1. 佈局目標函數加常理規則，並建立獨立評估指標與基準量測
2. 佈局失敗顯示
3. 拆成並行節點
4. 提示詞統整驗證迴圈
5. 評估節點的需求檢查與一鍵修正（提議模式）
6. 視第 1 項結果，再決定是否做 LLM 評審迴圈

所有新行為預設關閉。

## 5. 未來展望

- **對話式設計顧問**：把生成前澄清對話（`/api/requirement/clarify`、ClarifyChat）擴充成貫穿整條流程、能記住偏好的對話。內部模組成為它的工具，形成「面向使用者的協調者加專職工作者」。
  - 先做諮詢加提議，再做確認式代操作；不做無人確認版本。
  - 花錢與不可逆動作需使用者確認；以使用者本人權限執行；動作顯示在對話中；程式驗證工具參數；限制工具呼叫次數。
  - 偏好資料存 Supabase 並受 RLS 保護，使用者可查看與刪除。
- **渲染結果回饋**：評估不合格時調整提示詞或參數重生一次（見 3.3）。
- **風格與佈局溝通**：風格影響佈局傾向（見 3.4）；佈局的房間大小與採光補充風格檢索條件。
- **掃描輸入**：支援 LiDAR 掃描，取得準確的牆、門、窗尺寸，取代目前由 Gemini 偵測或推估的尺寸。
- **投影與照片吻合度檢查**：投影深度圖之後，檢查結果與照片的深度或分割是否吻合，差太多就提醒。
